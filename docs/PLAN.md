# GridNode: project plan

GridNode is an open-source SDK for modding Mirror's Edge Catalyst (Frostbite 3, codename *Pamplona*).
It has three parts that share one source of truth:

1. **libgridnode**: a C++ runtime library (loaded into the game) that lets a mod find, read, write,
   call and hook any engine class without reversing it first.
2. **GridNode Docs**: generated reference documentation for every class, field, enum and known
   virtual function, plus hand-written guides.
3. **GridNode Assets**: tools that move game assets (meshes, EBX data, levels) to and from open formats.

This plan is based on the material in `PreFindings/` (research.md, mec_reversing_notes.md, review.md,
the FrostbiteTypeDumper script and its PC outputs, the MECMP docs and the EBX XML dump) and on the
MECMP source in `D:\Dev\MECMP`. Status: **M0 to M3 done (2026-10-19).** See §8.

**Decisions**

| Topic | Decision |
|---|---|
| Platform | PC only. The game has not been updated in about 10 years, so there is one build to support. |
| Licence | MIT |
| Reflected type data | Generated by each user from their own install, never committed or published |
| Steam build | The Steam copy launches the game through the EA app, so it is the same exe. One build. |
| Lua scripting | Undecided; revisit after the C ABI (M5) |
| FrostbiteGen | Cross-check source only |

## 1. Goals and non-goals

**Goals**
- A mod author can write `OnCreated<PamClientCharacterEntity>(...)`, read Faith's transform, call
  `setVisible`, or hook a virtual function in a few lines, with no Ghidra session.
- Every fact the SDK uses lives in one database with its build, source and confidence, and the SDK,
  the docs and the Ghidra annotations are all generated from it.
- Reversing work flows both ways: Ghidra → database → SDK/docs, and database → Ghidra.
- MECMP is rebuilt on top of GridNode as its first real user.
- Long term: the same database and asset crates feed a Rust reimplementation.

**Non-goals (for v1)**
- No removing, patching or bypassing Denuvo or EA app activation. No code-byte patches at all.
- No touching the online backend (Beat Revival and similar must keep working).
- No redistributing game files, executable dumps or extracted assets.
- PC only. No PS4 support; the PS4 eboot and its notes stay a reverse-engineering reference.
- No multi-version support. One PC build, fixed addresses.
- No general Frostbite multi-game support. Catalyst first; keep the design open to other FB3 titles.

## 2. Ground rules taken from the findings

These come straight from what MECMP learned the hard way. The SDK enforces them so mod authors don't
have to rediscover them.

| Rule | Why (source) |
|---|---|
| **Hooks are pointer swaps only**: vtable slots, entity-creator slots, and game-owned function pointers (e.g. the stored `XInputGetState`). No inline/trampoline hooks by default. | The PC exe is Denuvo-protected and some functions are virtualised; MECMP never patches code (ARCHITECTURE.md "Rules"). An aligned 8-byte slot store is atomic on x64. |
| **Build check before anything is touched.** Compare known vtable slots and the first bytes of directly called functions; if anything differs, stay passive. | `fingerprint.cpp`. The EA app build loads at 0x140000000 with PE timestamp 0x5762e3b7 and SizeOfImage 0x727b000. |
| **One build, fixed addresses.** Store image VAs and rebase at runtime. The build check is only a safety net: on an unexpected exe GridNode stays passive instead of crashing. | The game is no longer updated. PS4 layouts differ from PC (Itanium tail padding vs MSVC), so PS4 offsets are never used. |
| **Engine calls happen on a game thread.** Server-side calls go inside the server tick; client-side writes inside the client updater. | Poses written from the render thread were read half old, half new (hooks.cpp comment). |
| **Data vs instance.** `entity+0x30` is the entity's *data* (a shared DataContainer). Writing it changes every entity that uses that asset. | MECMP copies `PamUseRunnersGhostShader` into the client entity (+0x334) instead of editing the shared data. |
| **Fault-tolerant access for anything the SDK didn't create.** Reads that might hit freed memory go through the safe path; virtual calls are checked to land inside the image. | `mem.h`, `gameVirtual()`. |
| **Server and client worlds both exist in single player.** Many objects come in Client/Server pairs; the SDK exposes both and says which realm a call needs. | research.md §2; creator realm 0 = client, 1 = server (calibration). |

## 4. Architecture

```
   user's game + gridnode.dll          Ghidra (dev only)
   ┌───────────────────────┐   ┌──────────────────────────────┐
   │ runtime TypeInfo dump │   │ FrostbiteTypeDumper│GridNodeSync│
   └──────────┬────────────┘   └─────────┬─────────┴─────▲─────┘
     reflected layer (local,       cross-check     annotations
     git-ignored)                                 (import/export)
              ▼                                         │
                 ┌────────────────────────────────────────┐
                 │  gridnode-db                            │
                 │  reflected/ (generated per user)        │
                 │  annotations/*.yaml (in the repo)       │
                 └───┬──────────────┬──────────────┬──────┘
                     ▼              ▼              ▼
              gridnode-gen     gridnode-gen    gridnode-gen
              C++ headers      docs site       Ghidra apply / fingerprints
                     ▼
              libgridnode  ◄── mods (MECMP, trainers, …) via C++ API / C ABI
                     ▲
              loader (version.dll proxy → mods/)
```

### 4.1 gridnode-db: the type database

Two layers:

- **Reflected layer** (generated on each user's machine, git-ignored, never published). Its producer
  is `gridnode-dump`: GridNode, loaded into the user's own running game, walks the live TypeInfo list
  (head `0x14215d028`) and writes the same JSON shape the Ghidra dumper writes, sorted by `ti`. No
  Ghidra, no exe dump, and it works on the Steam and EA app copies alike (they run the same exe). The Ghidra dumper stays as
  the developer tool for annotating Ghidra and as a cross-check (both must report 9,988 types).
- **Annotation layer** (hand-written YAML in the repo, one file per class or subsystem): our own
  reversing results, i.e. runtime class members, vtable slots, function signatures, globals, enums
  for magic values, notes. Annotations name reflected types but never copy their field lists, so the
  repo holds only our findings. They are validated against the user's reflected layer at generate time.

Every annotated fact carries `confidence` (confirmed / inferred / hypothesis, matching research.md),
`source` (decompile, in-game test, MECMP, FrostbiteGen), and the build(s) it was verified on.
The generator refuses to emit an unverified fact into the "stable" API; it goes into `gn::unstable`.

Example (`annotations/pamplona/PamClientCharacterEntity.yaml`):

```yaml
class: PamClientCharacterEntity        # must exist in the reflected layer
realm: client
size: 0x350                             # checked against the reflected size
vtable: 0x141c3c760
data: PamCharacterEntityData            # type of the object at +0x30
members:
  - { offset: 0x30,  name: data,             type: PamCharacterEntityData*, confidence: confirmed, source: mecmp }
  - { offset: 0x334, name: ghostShader,      type: bool, confidence: confirmed, source: mecmp,
      note: "Copy of data->PamUseRunnersGhostShader taken at creation. Write this, not the data." }
virtuals:
  - { slot: 0x108, name: getComponent, sig: "void*(TypeInfo* type)", fn: 0x1431c6eb0, confidence: confirmed }
  - { slot: 0x3d8, name: setVisible,   sig: "void(bool visible)",   fn: 0x143229480, confidence: confirmed }
properties:                              # handled by vf2 (property change by name hash)
  - { name: Visible, hash: 0x35bc69ab, type: bool }
verified: [pc-eaapp-5762e3b7]
```

### 4.2 gridnode-gen: generators

One tool (Python), run on the user's machine as part of setting up the SDK
(`gridnode setup`: load the game once with GridNode → dump → generate). The CMake configure step
fails with a clear message if no reflected layer exists yet. Outputs:

- **C++ headers** for libgridnode: typed structs with `static_assert`d offsets, vtable index enums,
  typed `Ptr<T>` wrappers, address tables per build, and the fingerprint list.
- **Docs pages** (one per class/enum/value type) with inheritance, fields, virtuals, which realm,
  confidence badges, and links to examples.
- **Ghidra apply script input**: names, struct types, vtable structs, function prototypes.
- **Fingerprint set** for the build check.
- **Reports**: annotations that don't match the reflected layer, and Ghidra-dump vs runtime-dump differences.

### 4.3 libgridnode: the runtime library

Modules, in build order:

| Module | Contents | Comes from |
|---|---|---|
| `gn::mem` | Safe/fast reads and writes, image data ranges, `patchPointer` | MECMP `mem.h` |
| `gn::build` | Build check (fingerprint), passive mode on an unexpected exe | MECMP `fingerprint.cpp` |
| `gn::reflect` | Walk the live TypeInfo list; find types by name; field lookup by name with offsets and types; enum names; `isKindOf` / `cast<T>` via classId ranges; read a field generically (`Value`) | dumper findings, MECMP `typeinfo` |
| `gn::hook` | One hook manager: vtable-slot hooks (shared vtables, so per-class not per-object), creator-slot hooks, function-pointer hooks; chaining so several mods hook the same slot; install checks; undo on unload | MECMP `hooks.cpp` |
| `gn::entity` | `OnCreated<T>` / `OnDestroyed<T>` for any class with a creator (1,103 known), live entity registry per class, transform get/set, `getComponent<T>`, data vs instance helpers | creator pattern + annotations |
| `gn::thread` | Server tick and client tick callbacks; `RunOnServer` / `RunOnClient` queues; asserts on the wrong thread in debug builds | `ServerGameWorld::postUpdate` slot, client replay updater (find a more general client hook) |
| `gn::events` | Fire events and set properties on entities by name (djb2-xor hash), so mods can drive the game's own logic wiring | research.md (needs PC `fireEvent` / property paths) |
| `gn::world` | Level/world lifecycle (`OnLevelLoaded`, current level name), local player, server player manager, camera, raycast, teleport | MECMP `level`, `local_player`, `camera`, `raycast`, `teleport` |
| `gn::ui` | ImGui overlay on the game's D3D11 swap chain, input capture, per-mod panels | MECMP `ui/overlay` |
| `gn::inspector` | In-game entity browser: list live entities by class, show reflected fields and annotated members, edit values, call annotated virtuals, follow pointers | new, built on `reflect` + `entity` |
| C ABI (`gridnode.h`) | Flat C functions over the above, so Rust and C# bindings (and Lua, if wanted later) can be written | new |

Sketch of the C++ API:

```cpp
#include <gridnode/gridnode.hpp>
using namespace gn;

GN_MOD("speedrun-trainer", "1.0.0");

void onLoad() {
    entity::onCreated<PamClientCharacterEntity>([](Ptr<PamClientCharacterEntity> ch) {
        log::info("character {} uses {}", ch, ch->data()->name());
    });

    hook::vtable<PamServerCharacterEntity>(&PamServerCharacterEntity::applyCustomization,
        [](auto original, auto self, auto& info) {
            log::info("customize {}", self);
            return original(self, info);
        });

    thread::onServerTick([](float dt) {
        if (auto me = world::localServerCharacter()) {
            static LinearTransform saved;
            if (input::pressed(VK_F5)) saved = me->transform();
            if (input::pressed(VK_F6)) me->teleport(saved);   // game's own teleport, game thread
        }
    });
}
```

Generic access for types nobody has wrapped yet:

```cpp
auto obj = reflect::Object(somePtr);           // type found with getType()
float h = obj["HealthOverride"].as<float>();  // reflected field by name
obj["Visible"] = true;                        // write through the reflected offset
```

### 4.4 Loader

- `version.dll` proxy (from MECMP `tools/proxy`) loads `gridnode.dll`, which runs the build check and
  then loads every DLL in `<game>/mods/` in dependency order.
- The standalone injector stays for development (inject after the main menu).
- One GridNode per process (named mutex), so two mods never bring two copies.
- Watch for the UAC VirtualStore redirect when the game is in Program Files (seen in MECMP testing):
  log path falls back to `%LOCALAPPDATA%\GridNode`.

### 4.5 GridNode Docs

- MkDocs (Material). Because reflected data is not published, there are two parts:
  - **published site**: guides, engine notes, and the annotated classes (our own findings);
  - **full reference**: one page per reflected class/enum/value type, built locally by
    `gridnode docs` from the user's reflected layer and merged with the annotated pages.
- Guides: getting started, threading and realms, data vs instance, hooking rules, writing a mod,
  contributing reversing findings (annotation format, confidence levels), building the SDK.
- Engine notes: entity/bus/blueprint model, spawn path, replay system, renderer, shader database,
  startup, all migrated from research.md and mec_reversing_notes.md with PS4 and PC addresses kept apart.
- Each class page shows its confidence and which builds it was verified on.

### 4.6 GridNode Assets (part 3)

Frosty Tool Suite already reads and writes Catalyst's archives and EBX, and supports mesh import.
GridNode should not repeat that. Plan:

1. **Assess first (M5 entry task):** check Frosty's licence and code for Catalyst support, and list
   what it cannot do for your goal (Blender → custom maps).
2. **Build only the gaps**, most likely:
   - lossless EBX ⇄ JSON/YAML round trip (diffable in git, scriptable);
   - a Blender add-on using glTF as the interchange format for meshes and level layout;
   - a headless CLI for batch export/import;
   - format specs in the docs (shader database is already partly documented).
3. Write the format code in Rust with Python bindings (PyO3), so the Blender add-on and a future
   Rust engine share it.

## 5. FrostbiteTypeDumper and Ghidra work

### 5.1 Fixes and checks on the dumper

From review.md, checked against the current script and outputs:

| Item | Status |
|---|---|
| ClassInfoData record overlap (0x48 vs 0x38) | Fixed: `applyData` now refuses to cross a known record start. |
| getType found by byte pattern; slot 0 as profile constant; vtable confirmed via `create` | Fixed (4,695 getType, 2,527 create-stored vtables). |
| Module names, `typeTi`/`superTi`/`elementTi` in JSON | Fixed. |
| Field `kind` key derived from field flags | Still emitted in JSON (`"kind"`). Remove it, or rename it, so tools don't trust it. |
| `String` (0x20) / `DbObject` (0x10) emitted as byte blobs | Partly fixed. Emit proper `fb::String` / `fb::Guid` structs in the header. |
| Profile address sanity check / auto-locate the list head | Not needed: there is one build. |
| PS4-only code paths (primitive array rule, PS4 profile) | Leave in place for the PS4 reference program; not used for GridNode. |
| Annotation stats | "records typed: 2" on a re-run is misleading because records already typed are not counted. Count them as "already typed". |
| Sorted, stable JSON for diffs | To add (sort by `ti`). |
| `--verify` pass (re-read random records) | To add. |

### 5.2 New Ghidra work

1. **Vtable structs in the C++ header** (they exist only in Ghidra today), named from annotations
   where known and `vf<slot>` otherwise.
2. **GridNodeSync script** (new, Java):
   - *import*: apply annotations to Ghidra (member structs for runtime classes, vtable slot names and
     prototypes, globals, comments with confidence and source);
   - *export*: write USER_DEFINED renames, prototypes and struct edits back as annotation YAML,
     marked `confidence: inferred, source: ghidra` until someone confirms them.
3. **Runtime class layouts**: create Ghidra structs for the fieldless runtime classes using the
   reflected size plus annotated members, so `this->data` and `this->vtbl->setVisible` read cleanly.
4. **Fingerprint generation**: for every function the SDK calls directly, record its first
   position-independent bytes (as `fingerprint.cpp` does by hand today).
5. **PS4 → PC name transfer**: research.md §8 has many PS4 names with no PC address yet. Match them
   through TypeInfo anchors, strings and call-graph shape (Version Tracking seeded with the `TI_`
   labels), so the knowledge carries over. The PS4 program is a source of names only.
6. **Conflict report**: where the reflected size, an annotation, MECMP and FrostbiteGen (cross-check
   only) disagree.

### Settings, console and messages (decided 2026-10-19)

Decision: expose everything; nothing is hidden. Settings and commands that touch online play
(NetworkSettings, Blaze/online environment, matchmaking) are shown with a warning and need a
confirmation before a write; mods get the same warning in the log.

Findings (Ghidra):
- `Console_executeCommand` (0x142a8a190) `(String* out, const char* line, bool trusted)`. With
  `trusted = 0` (the player's console) every command except `enable` / `disable` / `select` is
  refused unless `g_consoleEnabledForPlatform` is set. Config files run with `trusted = 1`
  (0x142a2f5d0 reads a file line by line, `#` comments, `sleep` and `afterloading` deferred through
  a queue run by 0x142a28c80), which skips that check. GridNode can call it the same way.
- Two command lists: static commands (`ConsoleRegistry_getStaticCommands` 0x142a91fc0; entries
  `{fn, name, group +0x10, args help +0x18}`) and bound commands
  (`ConsoleRegistry_getBoundCommands` 0x142a92040; 0x28-byte entries `{name, group, help, ctx, fn}`).
- Bound commands are settings fields: `ConsoleBinding_registerFieldsRecursive` (0x142a7e840)
  binds only fields with flag 0x2000 (116 in the dump) through `ConsoleFieldBinding_getOrSet`
  (0x142a7e1e0). Fields without the flag (most of the 105 settings classes) have no command, but
  their objects are live and readable by reflection: GridNode writes them directly.
- To do: the thread `Console_executeCommand` expects (the deferred queue's caller), where the
  settings objects are registered (the binding's +0x28 is the object), and why some commands work
  for players and others not.
- Messages: 764 message value types, 668 vtables already found by the walker; the message manager
  is the `MessageManager` global (+0x10 listener registry). Plan: register a GridNode listener
  object through the engine's own registration (no hook), filtered by category; mods receive the
  message with its fields readable by name.

### M5 notes

- Messages (Ghidra): three managers: `g_coreMessageManager` (0x142142ce0), and inline at +0x10 of
  `g_clientGameContext` (0x142401cb0) and `g_serverGameContext` (0x14253d670, until now called
  "MessageManager" in our annotations). `MessageManager_registerListener(manager, category,
  listener, realm)`; a listener is an object whose vtable has `onMessage(this, msg)` and an order
  (default 100); messages carry category (+8, djb2 of the category name), type id (+0xc, djb2 of
  the class name) and realm (+0x10). All 668 message types' static instances check out (offline,
  on the Scylla image): 120 categories, every name recovered.
- Built: `on_message` (API 4) by type or category, a listener per manager registered from the
  realm's tick (again if a manager is recreated), the inspector's Messages tab (record, counts, all
  types; a copy of each message's bytes), hello listens to ServerPlayer. Waiting for the in-game test.
- Message members after the 0x30-byte header are not reflected; annotating the useful ones is
  ongoing work. Entity-to-component messages (`Entity_sendMessageToComponents`) bypass the managers.

### M4.5 notes

- Built: settings from the `SettingsManager` by-type map (`settings_find`, an inspector Settings
  tab with every field editable), the console run with `trusted = 1` on the client thread
  (`console_run`, a Console window listing all static commands and bound settings fields),
  online warnings (settings classes and command groups; the menu asks before changing them, the
  log records every change a mod makes). API version 3.
- FrostbiteGen's CVars list (user data, not committed) matches the reflection: 135 settings
  classes, 3,431 fields, of which the console binds 141 (flag 0x2000). The rest are what players
  cannot reach; GridNode writes them directly.
- Setting a value through the console clones the settings object and hands the copy to the
  binding (`ConsoleFieldBinding_getOrSet`), so the manager may hold a new object afterwards;
  GridNode looks objects up again instead of keeping pointers. Direct writes change the live
  object; a system that copied a value at startup will not see them.
- Tested in game: settings edits work, console history works. The engine's own `list` and its error
  messages go to an internal log the shipping game does not show (`Console_executeCommand` writes
  them to a stream, not to the result), so GridNode answers `list` itself and reports unknown commands.
- MECMP is not ported to GridNode for now (decided 2026-10-19); it stays as it is.

### M4 notes

- Built: world API (local client and server characters, transforms, the game's teleport,

### M3 notes

- Client tick: `ClientGameWorld` vtable `0x141afe5f8` +0x28 (`0x14319f210`), the client counterpart
  of the server world's postUpdate; its only reference in the image. Confirmed in game.
- Mods get a C function table (`gridnode/api.h`), so they build with any compiler; C++ mods use
  `gridnode/mod.hpp`.
- Entity creators are bound to their classes when each realm's entity system starts
  (`EntityCreators_bindRealm` 0x143161af0), which can be after GridNode starts: `on_created` keeps
  its listeners and attaches them as creators appear, and the dump is rewritten once they settle.
- Client creators reach the class factory through a shared wrapper (vtable +8 = 0x14304bf60 ->
  0x143163210 -> +0x70 -> +0x40); server creators call it directly at +8. GridNode hooks +8 for both.
- Several characters share one `PamCharacterEntityData` (seen in game): data writes affect all of them.

### M1 findings

- In the running game every page of the image is committed and executable (Denuvo), so page
  protections cannot tell code from data. GridNode uses the PE section table for that, and
  treats the whole image as readable for fast reads.
- Deciding "code" by page protection made creator detection vary between runs (469 vs 1,103);
  with the section table it is deterministic.
- The dump takes about 0.35 s in game.

## 9. Risks

- **Denuvo / integrity checks.** Pointer swaps have been safe so far. Any new hook kind must be tested
  for a while in game before it's offered to mod authors.
- **Shared vtables.** A vtable hook affects every object of that class (and subclasses that inherit
  the slot). The hook API must say so, and give a filter (by object or by data).
- **Thread safety.** Most crashes in a mod SDK come from calling into the engine from the wrong
  thread. Debug builds should assert.
- **Legal/visibility.** Reflected data is generated by users, so the repo holds only code and our
  own findings. Keep the repo private until M5 anyway.
